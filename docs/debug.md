# Debug with LLDB

`ios --udid <UDID> debug <bundle-id> --local-app <path-to-local.app>` opens the device's iOS 17+ remote debugproxy through a userspace tunnel. It prints LLDB commands and stays in the foreground while one local LLDB client uses the temporary `127.0.0.1` port. Keep the command running; after the client disconnects the forwarding session ends. Ctrl+C cancels and closes the session. The endpoint accepts a local connection without authentication, so use it only on a trusted host.

Paste the printed lines into a compatible LLDB session. The generated `process launch` starts the selected app when executed; it is not executed by `ios`. Supply a local app bundle matching the installed app and debug symbols. If `--local-app` is omitted, the output contains `/path/to/local/application.app`, which must be replaced before use. Paths containing control characters are rejected; device paths containing a backslash are also rejected because Windows LLDB normalizes it as a separator. A failed RSD lookup or missing remote debugproxy is reported before app lookup; a compatible device and available service are prerequisites.

The loopback forwarding and script-generation behavior has host-side tests, but an actual LLDB session against a device exposing debugproxy has not been validated in the 2026-10-29 run. Windows LLDB displays the module platform path using Windows separators. Current LLVM source converts the launch path to the target's style only when its architecture triple has a known OS; the actual launch packet and compatibility with other LLDB versions remain unverified. See [Terra follow-up validation](validation/terra-followup-2026-10-29.md) for the device's observed service limitation.
